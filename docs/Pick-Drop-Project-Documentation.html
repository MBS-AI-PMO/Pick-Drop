1. What this product is

Pick-Drop is a school and commute transport system. A parent books a daily pick-up and drop for a child. A self user books the same kind of ride for themselves. A driver accepts the booking and runs the daily trip. An admin runs the web panel: approvals, assignment, payments, complaints, and emergencies.

There are four surfaces.

SurfaceWhoHow to test
Admin web panelAdmin staffBrowser
Driver appDriverMobile app, or Postman against /api/driver
Parent appParent of a studentMobile app, or Postman against /api/parent
Self appPerson riding for themselvesMobile app, or Postman against /api/self

Parent and Self use the same API shape. Only the prefix changes. A parent token must not work on /api/self, and a self token must not work on /api/parent. A driver token must not work on either.

2. Access

Ask the project owner for the live URL, the admin login, and the test accounts before you start. Do not invent production passwords.

Typical local admin URL when the project runs under XAMPP:

http://localhost/Pick-Drop/public

API base:

http://localhost/Pick-Drop/public/api

Health check, no login required:

GET /api/ping  →  { "status": "ok" }

Every protected API call needs these headers:

Authorization: Bearer <token>
Accept: application/json

File uploads (KYC, vehicle photos, payment screenshot) use multipart/form-data. Image files must be 5 MB or smaller.

Login returns a token. Use that token until logout. After logout the same token must be rejected.

3. Accounts and the order they must follow

A new user cannot book or drive until an admin approves them. Test this order. Skipping a step should fail with a clear error.

Driver

  1. POST /api/driver/register — name, phone, email, password. Referral code is optional.
  2. POST /api/driver/verify-email — OTP. Until email is verified, later steps stay blocked.
  3. POST /api/driver/verification — driver KYC. Required: date of birth, address, city, at least one service area, CNIC front, CNIC back, selfie, licence number, licence front, licence back, licence expiry (a future date), and terms accepted.
  4. Admin opens People → Driver KYC, reviews the documents, and approves or rejects.
  5. POST /api/driver/vehicle-verification — vehicle documents. Exact fields are in section 7.
  6. Admin opens People → Vehicle Verification and approves or rejects.
  7. The driver can go on duty with PUT /api/driver/me/duty and then see available requests.

Expected blocks:

  • Vehicle form before email verification → 403.
  • Vehicle form before KYC approval → 403. The message says to complete driver KYC first.
  • A second submit while the current one is pending → 422.
  • A submit after approval → 422.

Parent

  1. POST /api/parent/register
  2. Verify email.
  3. POST /api/parent/verification — date of birth, address, city, CNIC front, CNIC back, selfie, terms accepted.
  4. Admin approves under People → Parent / Self KYC.
  5. Add a student: POST /api/parent/students.
  6. Create a pick-up request. student_id is required. type must be parent.

Self

Same as parent, on /api/self, with these differences:

  • There are no students. The rider is the account itself.
  • A commute profile exists: GET and POST /api/self/commute-profile.
  • Request type must be self.

Forgot password

These three calls are separate: POST /api/driver/forgot-password, /api/parent/forgot-password, and /api/self/forgot-password.

  • A driver email on the parent or self forgot-password API must not receive a reset mail.
  • A parent email on the driver forgot-password API must not receive a reset mail.
  • An unknown email must not reveal that some other role owns that address.

5. Main journey — test this first

Run this once with a parent and once with a self user. This path must work before anything else is signed off.

  1. Admin has at least one city, one area, one vehicle category, and one charge.
  2. Parent or self registers, verifies email, and submits KYC.
  3. Admin approves KYC.
  4. Parent adds a student. Self skips this step.
  5. Parent or self creates a request with both a pick-up point and a drop point, times, and weekdays.
  6. The request appears in the app list and in Admin → Pickup Requests.
  7. An approved driver who is on duty sees it in GET /api/driver/requests/available.
  8. The driver accepts it. The parent sees the driver on GET /api/parent/requests/{id}/driver.
  9. On the ride day, the driver opens GET /api/driver/rides/today.
  10. The driver starts the ride: POST /api/driver/rides/{pickup_request_id}/start.
  11. The driver sends location: POST /api/driver/location/update. Parent tracking (GET .../tracking) shows the new point.
  12. The driver marks pick-up, then drop.
  13. GET /api/driver/rides/today shows trip.can_end = true.
  14. The driver ends the trip: POST /api/driver/rides/end.
  15. The parent rates the driver. The driver can rate the request.
  16. Admin creates or sends the invoice. The parent pays by screenshot. Admin marks the receipt received. The invoice becomes paid.
If step 13 stays false, do not force the end call. Read trip.end_blocked_reason and trip.pending_passengers. Those names are the passengers who are still not dropped and not marked as not going.

6. Booking rules

Create a booking with POST /api/parent/requests or POST /api/self/requests.

service_type is one of:

ValueMeaning
bothMorning pick-up and afternoon drop. This is the default.
pickup_onlyPick-up only.
drop_onlyDrop only.

trip_mode is round_trip or one_way.

For a normal booking (no stops array):

  • type is required and must match the app (parent or self).
  • city_id is required.
  • Pick-up point, pick-up latitude and longitude, drop point, and drop latitude and longitude are required.
  • Both locations are required even when the service is pick-up only or drop only.
  • days is a non-empty list of weekdays.
  • Pick-up time (H:i, example 07:30) is required unless the service is drop only.
  • Drop time is required unless the service is pick-up only.
  • Parent requests need a student_id that belongs to that parent.

An optional multi-stop body uses stops[] with type (pickup or drop), point, lat, and lng. Maximum 20 stops.

After create, also test:

  • List the request and open it.
  • Edit it before a driver is locked in.
  • Cancel it. Call cancellation preview first: GET .../cancellation-preview.
  • Renew, turn auto-renew on and off, and decline renewal.
  • Skip a day (POST .../attendance/skip) and undo it.
  • A skipped day must not appear as a normal ride for the driver.

8. Daily trip, end trip, not going, and emergency

These are the newest driver rules. When you can, test them on a day that has at least two accepted passengers.

Today screen

GET /api/driver/rides/today

Each passenger includes:

  • passenger_status: waiting, picked, dropped, or not_going
  • not_going_reason
  • can_mark_not_going — true only after the trip has started, and only if that passenger is not already picked and not already marked not going

The trip object includes:

  • can_end
  • end_blocked_reason
  • emergency_open
  • pending_passengers — names still not settled
  • Counts: total, picked, dropped, not going

The app should show the End Trip button only when can_end is true.

Start and finish a passenger

CallWhen

POST /api/driver/rides/{id}/arriveDriver reached the point
POST /api/driver/rides/{ride}/pickupPassenger is in the vehicle

9. Payments

Field-level notes are also in postman/PAYMENT-API-CHANGES.md. The same calls exist for parent and self. Examples below use the parent prefix.

  1. GET /api/parent/payment-methods — bank, JazzCash, and EasyPaisa details the app should show.
  2. GET /api/parent/invoices and GET /api/parent/invoices/{id}.
  3. The user pays outside the app, then calls POST /api/parent/invoices/{id}/pay/screenshot.
    • proof image is required.
    • method is optional: bank_transfer, jazzcash, easypaisa, or manual.
    • reference and notes are optional.
  4. The response status is not_received. The invoice is not paid yet.
  5. Admin opens Payments, reviews the screenshot, and marks it received.
  6. The app calls GET /api/parent/invoices/{id}/pay/status. receipt_status is received and paid is true.

13. Cross-checks

  • A parent token on /api/driver/... returns 401 or 403.
  • A driver token on /api/parent/... returns 401 or 403.
  • A parent token on /api/self/... returns an account-type error.
  • Request type=self from the parent app is rejected.
  • Two drivers accepting the same request: only the first succeeds.
  • Ending a trip while one child is still in the vehicle is rejected.
  • An SOS during a trip blocks the driver end button until an admin ends the trip.
  • Owner document front and back are not required.
  • A payment screenshot does not mark the invoice paid until an admin confirms it.
  • A holiday date does not generate a normal ride.
  • After logout, the old token fails.

14. How to report a bug

Include all of these:

  1. Surface: Admin, Driver app, Parent app, or Self app.
  2. Account email and role used.
  3. Numbered steps.
  4. Request method and path, if it is an API bug.
  5. Response status code and the message field.
  6. Expected result, taken from this document.
  7. Actual result.
  8. Screenshot or the response body.
  9. Time of the test.
LevelMeaning
BlockerRegister, login, booking, accept, pay, or trip end cannot be completed.
MajorA rule in the vehicle, trip, or payment sections fails.
MinorWrong text, layout, or a field that is saved but displayed incorrectly.
NoteThe message is unclear. The feature still works.
